# How to repeat the performance measurements

For section E2 of the GP2 report. What is automated, what is manual, and what has not been measured yet.

Record for every run: Chrome version (`chrome://version`), machine, CPU, RAM, the commit of the build, and the runtime line described in step 2.

## 1. Analysis time by prompt size, outside the browser (automated)

```bash
node eval/accuracy/build-dataset.mjs
npx vitest run -c vitest.eval.config.ts eval/perf.eval.ts
```

Writes `docs/gp2-evidence/performance/node-timing.json`: rules only, and rules plus the detection model, for 100, 1,000 and 5,000 characters, 50 runs each, with the number of runs over 2,500 ms. Close other programs first; the model figures move a lot on a busy machine. This is the Node runtime, not the browser.

## 2. Time of one check in the browser (manual, the extension prints it)

1. Load `.output/chrome-mv3`, sign in, open ChatGPT, press F12 and open the Console.
2. Send a message. The extension prints one line per check:
   `[hares] check took 1140 ms (policy 737 ms, detection 93, 2 topics 290; model times are the worker's own)`
   - *check took*: the whole wait before the message is sent or the dialog opens.
   - *policy*: the wait for the policy check.
   - *detection*, *topics*: time inside each model.
3. For the three sizes, paste a prompt of 100, 1,000 and 5,000 characters built from sentences of `docs/gp2-evidence/accuracy/dataset.json` (generated by step 1, not committed), 50 times each, and copy the lines. A check where the detection model shows `timeout` instead of a number hit the 2,500 ms limit.
4. Whether several threads are in use: in `chrome://extensions`, open **offscreen.html** under "Inspect views" and run `crossOriginIsolated` in its console. `true` means the models may use several threads. The number of threads is not printed by the product build; the experiment build on the branch `experiment/wasm-threads` adds it to the line (`isolated=true threads=4 cores=12`).

Rules-only time inside the browser is not printed separately. It is part of *check took* when the policy has no TOPIC rules and the detection model is switched off; there is no switch for that in the popup, so this number has not been taken in the browser.

## 3. Time from send to the dialog (manual)

Paste this in the page console once, then send a message that opens a dialog:

```js
window.__h = [];
addEventListener('keyup', (e) => { if (e.key === 'Enter') __h.push(['enter', Math.round(performance.now())]); }, true);
new MutationObserver((ms) => { for (const m of ms) for (const n of m.addedNodes) if (/hares/.test(n.id || '')) __h.push([n.id, Math.round(performance.now())]); }).observe(document.documentElement, { childList: true, subtree: true });
```

`__h` then holds the time of Enter and of `hares-dialog` (or `hares-toast`) appearing. The difference is the time to the dialog. Enter is recorded on key release, so the figure is short by the length of the key press.

## 4. Model load time (manual)

- From cache: reload the extension, open **offscreen.html** and read
  `[hares] detection model ready in … ms` and `[hares] topic model ready in … ms` (the second appears once a policy with a TOPIC rule is seen).
- First load with download: remove the extension, add it again (this clears the stored models and the sign-in), and read the same two lines. **Not measured yet.** This run also answers whether the download works with cross-origin isolation on.

## 5. Memory (manual, not measured yet)

1. Open Chrome's task manager (Shift+Esc). Find the rows "Extension: Hares AI" (the service worker) and the offscreen document of Hares AI.
2. Note "Memory footprint" of both: right after reloading the extension, before any chat page is opened; after `detection model ready`; after `topic model ready`; and after 50 messages.

## 6. Other machines and platforms (not measured yet)

Repeat steps 2 to 5 on a machine with 4 cores or fewer, and on Claude and Gemini.

## 7. Size of the build

npm run build
du -sh .output/chrome-mv3 .output/chrome-mv3/wasm
